# AICHONG 决策记录

更新时间：2026-05-28
用途：记录我们为什么做过某些决定，减少新线程只知道“结果”却不知道“原因”。

## 记录规则

- 这里只记录影响项目方向、协作方式、业务规则、上线风险的重要决定。
- 临时实现细节不必全部写入。
- 如果后续改变决定，新增一条新的记录，不直接抹掉旧原因。

## D-001：AICHONG 用户侧不暴露才虫内部集成

决定：前台用户体验应表现为 AICHONG 自己在服务用户，不主动暴露才虫 API、同步机制、内部任务市场等技术细节。

原因：普通用户不需要理解背后供应链。暴露内部集成会增加困惑，也会削弱 AICHONG 自己的产品关系。

影响：前台文案要偏用户结果和订单进展，不写“调用才虫接口”“同步到本地”等内部话术。

## D-002：第一版先走平台代理 Agent，不做独立用户 Agent 模式

决定：第一版不做每个用户自己的独立 Agent 模式，先走平台统一代理能力。

原因：第一版目标是跑通真实业务闭环。如果过早引入用户独立 Agent，会增加账号、权限、支付、结算和支持复杂度。

影响：用户只需要在 AICHONG 发单，不需要理解或管理 Agent。

## D-003：聊天不是长期记忆，重要规则必须写进文档

决定：项目重要规则、当前状态、上线结论、风险判断和测试结果必须写入文档，不能只留在聊天线程里。

原因：多线程和记忆压缩会导致上下文丢失。聊天适合沟通，文档才适合作为长期项目记忆。

影响：新线程先读固定入口文档；线程结束时要写回重要结论。

## D-004：钱、短信、结算、权限、生产配置永远先问主人

决定：涉及真实付款、真实短信、真实结算、权限边界和生产配置的动作，Codex 永远必须先问主人。

原因：这些动作影响真实用户、真实成本、资金结算、数据安全和生产稳定，不能由 Codex 根据“看起来合理”自行决定。

影响：即使是测试或修 bug，只要会触发这些高风险动作，也必须先得到主人明确同意。

## D-005：Harness 第一阶段只做安全检查

决定：Harness 第一阶段只做安全检查和验收展示，不自动触发真实付款、真实短信或真实结算。

原因：当前最需要的是让主人看见项目健康度和风险，不是让系统自动执行高风险业务动作。

影响：第一阶段 Harness 可以检查配置、健康、权限、日志、同步状态，但不能自动完成真实付款、发短信或采用投稿。

## D-006：上线必须有上线总控结论

决定：功能线程完成和测试线程建议上线，都不能直接代表可以上线；最终需要上线总控明确给出“可上线”。

原因：不同线程只看到局部，容易遗漏本轮改动范围、生产配置、数据库迁移、权限和真实业务风险。

影响：上线前必须看本轮包含什么、不包含什么、验证结果和残留风险。

## D-007：短信提醒主调度使用外部 5 分钟 Cron，GitHub Actions 只做兜底

决定：订单短信提醒的主调度推荐使用外部 HTTP Cron 每 5 分钟触发，GitHub Actions 30 分钟任务只作为兜底。

原因：GitHub Actions 定时调度不够稳定，曾出现较长时间间隔，不适合作为用户提醒的唯一近实时来源。

影响：生产环境需要配置专用 `ORDER_REMINDER_CRON_SECRET`，外部 Cron 只拿专用密钥，不优先使用总 `CRON_SECRET`。

## D-008：前台普通登录和后台管理员登录必须隔离

决定：前台普通用户登录态和后台管理员登录态必须隔离，不能互相覆盖。

原因：曾出现同一浏览器后台登录管理员后影响前台用户身份的风险，可能导致订单详情无权限或身份错乱。

影响：前台继续使用普通用户登录态，后台使用后台专用登录态；后台退出不影响前台登录。

## D-009：真实采用投稿必须由人类明确确认

决定：选择投稿和采用投稿不能由系统自动完成，必须由人类明确确认。

原因：采用投稿会影响订单结果和结算，属于资金与用户权益相关动作。

影响：前端必须有确认弹窗；后台、Harness、自动化流程都不能绕过主人确认直接触发采用投稿。

## D-010：界面图标必须来自指定 Figma 图标库

决定：所有界面需要图标时，必须从指定 Figma 图标库 `yWZTSzMR9aC8l9DBljE31C` 查找并使用。Codex 不得自行绘制图标、手写临时 SVG、模仿替代图标，或擅自换成其他图标风格。

原因：过去线程曾反复在图标上自行发挥，导致界面风格不统一，也破坏了已确认的设计资产来源。

影响：如果 Figma 图标库里找不到合适图标，Codex 必须先说明缺口并询问主人，不能静默创建替代方案。
