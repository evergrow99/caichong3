# Collaboration Playbook

这份文档记录项目协作经验，目标是让非程序员也能稳定调度多个开发线程、测试线程和上线总控，减少重复解释。

## 三句核心口令

给功能线程：

```text
交接给上线总控，按上线摘要整理。
```

作用：让功能线程说明改了什么、影响哪里、验证了什么、还有什么风险。

给测试线程：

```text
读当前测试摘要，按上线摘要测试，能修就修。
```

作用：让测试线程按指定范围测试，发现问题后尽量修复，并提交测试结论。

给上线总控：

```text
收测试结论，做上线总控。
```

作用：让上线总控汇总所有摘要、复查代码、评估风险，最后判断能不能上线。

## 最省心的协作流程

1. 功能线程开发完，先交上线摘要。
2. 上线总控整理本轮待测范围，写入 `docs/current-release-test-brief.md`。
3. 测试线程读取测试摘要，测试、修 bug、提交测试结论。
4. 上线总控二次评审：看代码差异、跑构建、查风险点。
5. 上线总控给出结论：可上线、补测后上线、暂缓上线。

## 你只需要盯住的四件事

- 谁在做功能。
- 谁在做测试。
- 哪一版准备上线。
- 上线总控是否明确说“可上线”。

如果没有“可上线”结论，不要默认上线。

## 什么时候要特别小心

只要涉及下面内容，就让上线总控重点复查：

- 付款、退款、结算。
- 短信、通知、定时任务。
- 用户登录、管理员权限。
- 订单、投稿、附件下载。
- 数据库迁移、环境变量、密钥。

这些地方出错，通常不是“界面不好看”，而是可能影响钱、数据、安全或真实用户。

## 一个好用的判断标准

功能线程说“做完了”，只代表代码可能完成。

测试线程说“测过了”，代表主要路径可能可用。

上线总控说“可上线”，才代表这一版经过汇总、复查和风险判断。

## 更好的习惯

- 每轮上线只收一个明确版本，不把零散改动偷偷混进去。
- 每个线程都说清楚“改了什么”和“没测什么”。
- 测试线程修过 bug 后，必须重新交测试结论。
- 上线前保留一份上线摘要，方便出问题时回看。
- 上线后观察健康检查、日志、定时任务和真实用户路径。

## 以后开新项目也能复用

新项目开始时，可以先建立三份文档：

- `docs/release-management.md`：上线标准和风险门槛。
- `docs/current-release-test-brief.md`：当前版本给测试线程的摘要。
- `docs/collaboration-playbook.md`：协作口令和分工方式。

这三份文档能让不同线程知道自己该做什么，也让你不用记住开发细节。
